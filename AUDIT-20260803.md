# Grouse codebase audit — 2026-08-03

Method: direct read of every source file after the MCP-App/steering/probe commit (45123b6).
Coverage: ~8,200 lines across 20 Kotlin files + manifest + XML resources.

---

## P0 — bugs, will bite

### P0.1 ConnectionManager inherits a stale `pendingRecipeId` across open() calls

`pendingRecipeId` is read-and-cleared inside `open()` at line 1257, but it is declared
as a property of the `ConnectionManager` companion/class (file-level, not scoped to a
single open → Ready cycle). If `open() is called twice in quick succession (foreground
probe→reconnect path can race with a user-initiated session switch), two concurrent
`open()` calls both see the same `pendingRecipeId`, and the second one sends it to the
wrong client.

**Fix:** scope `pendingRecipeId` to the `clientGen` that consumed it, or clear it
immediately on read rather than after the `also` block.

### P0.2 `rpc()` null-return path leaks `register` side effects

In `AcpClient.rpc()` (line 808), the `register` lambda is called BEFORE the `ws` null
check:
```kotlin
register?.invoke(id)       // bookkeeping happens
sock.send(...)             // then fails if ws was null
```
If `ws` is null, `register` has already stashed its mapping (e.g. in
`pendingExtListSids`). The id is never answered, so the entry leaks forever and the
next login/extensions list for that target id will never arrive.

**Fix:** move the `register` call after the null check, or clean it up if `ws == null`.

### P0.3 `pendingPushSessionId` is not cleared on TurnDone

`pendingPushSessionId` is set when a prompt is sent (ConnectionManager `dispatch`,
line 997: `lastSessionId?.let { store.pendingPushSessionId = it }`). It is never
cleared on TurnDone. If the app is killed after the turn completes but before the next
prompt, the stale id persists and a subsequent push notification from any client's turn
in that session will match it (the filter is `store.pendingPushSessionId == pushed sessionId`).

**Fix:** clear `store.pendingPushSessionId = null` in the `TurnDone` handler.

### P0.4 `probeToken` is a per-ConnectionManager counter, not per-session

The probe token (line 547) is a single `Int` on ConnectionManager. Two sessions
probed in rapid succession (e.g. foreground event triggers a probe for session A, while
a `turnResyncTick` fires a probe for session B) would race: the `++probeToken` for
session B cancels the pending timeout for session A, even though session A's probe is
still outstanding. The 2.5s timeout then fires and forces a reconnect for the wrong
session, or never fires for the one that actually timed out.

**Fix:** scope `probeToken` per session, or use a `Map<String, Int>`.

### P0.5 `transcriptCacheFile` session-id collision

`transcriptCacheFile` (line 1167) sanitizes the session id with
`sid.replace(Regex("[^A-Za-z0-9_-]"), "_")`. Two session ids that differ only in
special characters (e.g. `abc-def` and `abc_def` both become `abc_def`) would write
to the same cache file, corrupting the cold-start transcript.

**Fix:** use the session id hash (MD5 or SHA-1) as the filename, or encode
with URL-safe base64.

## P1 — should fix

### P1.1 `McpAppView` JSInterface is uncacheable

Each `McpAppView` composable creates a fresh `WebView` with a fresh
`addJavascriptInterface` bridge. The `guestHtml()` and `toolInput()` methods return
the message's content at the time of the JS call. If the `ChatMessage` is updated
(e.g. `appHtml` arrives later from the cache), the WebView already has the old
`srcdoc` and the bridge returns the old empty string. The code handles this by
setting `srcdoc` only once in the `factory` block, but if the template arrives
after the WebView is created, the `appHtml` field on the `ChatMessage` is updated
(via the `copy()` in `ConnectionManager.onEvent`), but the WebView is already
rendered with the empty string.

**Fix:** observe `m.appHtml` and call `loadDataWithBaseURL` again when it changes,
or use a `LaunchedEffect` on `m.appHtml` to inject the content via
`evaluateJavascript`.

### P1.2 `saveTranscriptCache` writes but never prunes

The transcript cache writes to `transcripts/<sid>.json` on every focus loss but
never deletes old files. Over time, every session the user opens accumulates a
cached transcript. For a 60-message limit per file this is a slow leak (a few KB
per session), but combined with the collision bug (P0.5) it means stale files
accumulate indefinitely.

**Fix:** delete the file for the old session when switching sessions, or maintain
a last-used LRU of ≤20 entries.

### P1.3 `discovering` is a nullable `String?` but never cleared on error

The `discovering` state variable (ConnectionManager, set by `discoverTools`) is
cleared on success but not on error. If a `tools/list` fails during discovery,
`discovering` stays set, and the NEXT tools/list reply (for a different extension)
triggers a spurious `setSessionTools` write. This was noted in the previous audit
(ACP-AUDIT-20260803.md, finding 8) and the `background` error handler now clears
`discovering` for `_goose/unstable/tools/list` errors, but only in the background
path — a foreground `tools/list` error still leaves it stuck.

**Fix:** clear `discovering` in the `else` branch of the AcpEvent.Error handler
too, or add a `finally`-style cleanup in the discover method.

### P1.4 `extensionsBusy` is never cleared on error

Same pattern as `discovering`. `extensionsBusy` is set to `true` before a
`listSessionExtensions` call and only cleared on success. A failed call leaves the
extensions sheet permanently spinning. The background error handler clears it for
`config/extensions/list` errors (same code block), but a foreground failure is
uncovered.

**Fix:** same as P1.3 — clear in the non-background error path too.

### P1.5 `handleEntry` trusts `ACTION_OPEN_SESSION` without verifying the sender

`MainActivity.handleEntry` (line 78) reads `pendingOpenSession` from an intent
extra. The `ACTION_OPEN_SESSION` intent filter is NOT declared in the manifest
(only `NEW_CHAT` is), so only explicit intents can reach it — but any app with
`<queries>` access or the package name can fire an explicit intent. A malicious
app could force Grouse to open an arbitrary session id, potentially leaking the
session's first message snippet (which is shown in the drawer).

**Fix:** either register the intent filter with a permission, or validate the
session id format (UUID regex) before accepting it.

### P1.6 `ConnectionManager.t()` returns different lists during replay

The `t()` function (line 465) returns `replayBuffer` during replay and `messages`
otherwise. Callers that iterate `t()` and then mutate the returned list (e.g.
`t().add(...)`) are vulnerable to the list changing under them if the replay
completes mid-iteration. The current code is safe because `replayActive` is only
set and cleared in the event handler thread (main handler), but the invariant is
fragile.

**Fix:** make `t()` return a snapshot copy, or make the dispatch explicit
(`messages.add(...)` vs `replayBuffer.add(...)`) at each call site so the illusion
isn't relied upon.

## P2 — worth doing

### P2.1 Screens.kt is 3,372 lines — should be split by feature

Every screen, dialog, sheet, and utility composable lives in one file. The
`DrawerChats` composable (~150 lines), `ChatScreen` (~300+), `SettingsScreen`
(~200+), `McpAppView` (~100), `ChartView` (~60), and all the recipe/skill/schedule
screens are in the same file. This makes it impossible to navigate, review, or
test independently.

**Split by feature:** `screens/chat/`, `screens/settings/`, `screens/skills/`,
`screens/recipes/`, `screens/charts/`, `screens/mcpapp/`.

### P2.2 ConnectionManager is 1,688 lines — a god object

ConnectionManager owns: sessions, the queue, voice/TTS, notifications, push
registration, the transcript cache, the file browser, the MCP-App template cache,
the tool discovery, the extension list, the lifecycle, and the network connection.
These are ~8 distinct concerns. The replay buffer swap and the `t()` multiplexer
are the most fragile part.

**Split:** extract VoiceManager (TTS + speech), Notifier (notifications — already
partially separate), FileBrowser (browser session + state), and ToolDiscovery
(discover + setSessionTools).

### P2.3 AcpClient.kt mixes data classes with protocol logic

`AcpEvent` (a sealed interface with 30+ variants), `SessionInfo`, `ProjectInfo`,
`ScheduleInfo`, `RecipeInfo`, `SkillInfo`, `ExtInfo`, `RecipeParam`, `ImageBlock`,
`ConfigOption`, `PermOption`, `Choice` — all defined in the same file as the
protocol handler. These are ~400 lines of type definitions that don't change with
the wire logic.

**Fix:** move to `acp/Events.kt`, `acp/Types.kt`.

### P2.4 `listSessions()` is actually `listSessionsAndProjects()`

`ConnectionManager.listSessions()` (line 565) calls both `client?.listSessions()`
and `client?.listProjects()`. The name is misleading — a developer reading call
sites will think they're only refreshing the session list. This is a bug waiting
to happen if someone adds a read-only session list operation.

**Fix:** rename to `refreshSidebar()` or split into two explicit calls at the
two call sites.

### P2.5 `gooseUpdate` and `standardUpdate` in AcpClient are the same shape

`AcpClient.gooseUpdate()` (line 1333) and `standardUpdate()` (line 1356) parse the
same notification payload (`params._meta.goose` and `params._meta.standard`). They
both produce `AcpEvent.MessageUsage`. The double-emission is documented as a server
transition (goose emits both; clients should migrate off `gooseUpdate`). Once the
server stops emitting the `goose` variant, `gooseUpdate` is dead code. It has no
caller that checks specifically for it.

**Fix:** remove `gooseUpdate` and the `usage_update` notification branch for
`_meta.goose`. The `standard` update is the canonical path.

### P2.6 `Net.kt` trust-all TLS is a single point of failure for the security model

`Net.kt` trusts every TLS cert and every hostname. The comment says "tailnet-only"
and "secret key for auth" — but the secret key is sent over this TLS connection.
A MITM on the LAN or a compromised DNS on the tailnet can intercept the key. While
this is a documented trade-off (self-signed certs would need re-pinning on every
cert regeneration), it's worth noting that the hostname verifier adds no value at
`{ _, _ -> true }`. At minimum, the hostnameVerifier could verify the host against
the stored `host` preference.

**Fix:** replace `hostnameVerifier { _, _ -> true }` with a verifier that checks
the hostname matches `store.host`. This still trusts the LAN for the cert, but
prevents DNS-based MITM.

### P2.7 `usesCleartextTraffic="true"` in the manifest is broader than needed

The app only needs cleartext for the LocalAI HTTP server (`http://host:8080`).
Setting `usesCleartextTraffic` on the whole app means any cleartext URL the app
might load (e.g. from a server response, or from a WebView guest) is permitted.
Android's network security config can narrow this to specific domains.

**Fix:** replace the manifest flag with `network_security_config.xml` that
allows cleartext only for the LocalAI host.

## Summary

| Severity | Count | Notable |
|----------|-------|---------|
| P0 (bug) | 5 | stale `pendingRecipeId`, leaked `register` side effects, uncleared `pendingPushSessionId`, racing probe tokens, transcript cache collision |
| P1 (should fix) | 6 | WebView cache miss, transcript cache never prunes, stuck flags on error, intent validation, fragile `t()` semantics |
| P2 (nice to have) | 7 | Screens.kt split, ConnectionManager god object, AcpClient data class extraction, misleading function name, dead code path, TLS verification, cleartext scope |

The codebase is well-structured and well-commented. The bugs are concentrated in
the newer features (probe, steering, transcript cache, MCP-App) and the classic
race-condition territory of the ConnectionManager singleton. The security posture
is reasonable for a tailnet-only app, with two notable gaps: the trust-all TLS
(which is a conscious trade-off) and the missing intent validation on
`ACTION_OPEN_SESSION`.
