# ACP coverage & cleanliness audit — 2026-08-03

Method: two parallel sweeps — one enumerating goose's full ACP surface from source
(`~/dev/goose`, 116 request methods, 13 notification variants, 10 server→client requests),
one enumerating what AcpClient.kt/ConnectionManager.kt send, handle, and drop — then a diff.
Coverage breadth is fine (~45 methods, the rest are Desktop onboarding/provider-setup
surface a phone client doesn't want). The findings are correctness and hygiene.

## P0 — real bugs, bite today

1. **Every background RPC error becomes a chat bubble and clears turn state.**
   `AcpEvent.Error` handling in ConnectionManager (~L1186) adds an "error" message to the
   OPEN TRANSCRIPT and resets `busy`/`turnInFlight`/`compacting` — for ANY failed call,
   including a sidebar `schedules/list` refresh. A background failure visibly corrupts the
   conversation and can un-busy a live turn. Errors need routing: turn-scoped calls to the
   transcript, everything else to a toast/log.

2. **Parameterized recipes hard-fail from Grouse.** Server-side: if a recipe declares
   `parameters` and the client did not declare `_meta.goose.recipeParameterRequests` in
   initialize, `session/new` fails with invalid_params (recipe/mod.rs:378). Grouse doesn't
   declare it and doesn't handle the `_goose/unstable/session/recipe/request-params`
   server request. "Start session" on any recipe with parameters = opaque error. Fix =
   declare the capability + a params dialog (reuse the elicitation form UI).

3. **Deleting a skill never refreshes the skills list.** `sources/delete` is sent with the
   default tag for BOTH projects and skills; the single reply branch calls `listProjects()`.
   The `#skill` tag mechanism exists for exactly this (sources/list uses it) and isn't
   applied to delete. Skill rows persist until an unrelated refresh.

4. **The file-browser client hangs server requests forever.** Its event handler answers
   neither Permission nor Elicitation — the server request id is registered and never
   answered. The boot/utility client auto-cancels elicitations but not permissions. Any
   browse that trips smart_approve freezes that server-side request.

5. **MCP-App fetch failure wedges the bubble** (today's feature): `appFetchInFlight` is
   only cleared on success; an errored `resources/read` blocks retry permanently and the
   bubble stays a bare tool row. Error path must clear the in-flight marker; an empty
   `AppResource` should allow a later retry.

## P1 — protocol hygiene (ALL FIXED 2026-08-03)

6. **Unknown server→client requests are answered `{}`** — a structurally invalid result
   (e.g. for `fs/read_text_file` it lacks `content`). Should be JSON-RPC `-32601`. Same
   for `session/request_permission` missing a toolCallId: `respond(id, {})` is not a valid
   RequestPermissionResponse — answer `{outcome:{outcome:"cancelled"}}`.

7. **String JSON-RPC ids are silently dropped.** `id.jsonPrimitive.intOrNull` → null →
   reply discarded and `pending` entries leak. Spec allows string ids; goose uses ints
   today, so this is a time bomb, not a fire.

8. **Stuck flags on error paths**: `discovering` (tools/list error mid-discovery makes the
   NEXT tools/list reply trigger a spurious `setSessionTools` write), `extensionsBusy`
   (sticks true), `pendingExtListSids`/`pendingToolListSids` (not cleaned on error — only
   `pendingConfigKeys` is). Also: those two sid maps are written AFTER `rpc()` puts the
   frame on the wire — the exact fast-localhost race `readConfig` was explicitly rewritten
   to avoid. Latent (the racy paths are currently dead), but it contradicts the file's own
   documented lesson.

9. **`rpc()` leaks `pending[id]` when `ws` is null.** Record after send, or clean on null.

10. **RESOLVED SAFE — `toExtensionDto` casing verified against the server DTO.**
    `GooseExtension` (custom_requests.rs:391) has NO `rename_all`: `available_tools` is
    genuinely snake_case on the wire, and `env_keys` carries an explicit
    `#[serde(rename = "envKeys")]`. The DTO itself is mixed-case and Grouse's "inconsistent"
    serializer matches it field-for-field. Allowlists were never being dropped.

11. **Casing map, confirmed server-side** (for the bitten-list): bare snake_case params on
    ALL 10 `recipes/*`, `schedules/list` + `schedules/create`, `config/extensions/list`,
    `extensions/available`, `dictation/config`; the other 8 `schedules/*` are camelCase.
    Grouse's current calls all match; the trap is future calls.

## P2 — worth implementing, in value order (12-16 IMPLEMENTED, 17 placeholder-only, 2026-08-03)

12. **Steering** (`session/steer` + `expectedRunId`): true mid-turn injection, vs today's
    client-side queue. Requires parsing `session_info_update._meta.goose.activeRunId` /
    `queuedSteer` — the notification is already received and those keys ignored. This is
    the overloaded notification: three payloads (title updates, active-run lifecycle,
    queued-steer acks) distinguished only by which `_meta` keys are present.
13. **`toolCallLabelEnrichment` capability** — declare one flag in initialize, get 1.45's
    enriched tool-call labels for free.
14. **`_meta.goose.includeLastMessageSnippet` on session/list** — drawer previews, one flag.
15. **Live shell output**: `tool_call_update._meta.toolNotification` tagged union
    (`live_output` streams shell). Currently only `content[].text` is read — long shell
    runs are invisible until they finish.
16. **`session/export` / `import`** — chat backup path, trivial to wire.
17. **Non-text content blocks in agent messages** are dropped (agent-sent images render as
    nothing). Rare with current models; cheap placeholder at minimum.

## Server-side facts worth keeping (they shape client behavior)

- `_goose/unstable/session/update` notifications are gated on
  `clientCapabilities._meta.goose.customNotifications` — Grouse declares it (that's why
  per-message tok/s works). The standard `usage_update` is dual-emitted with an explicit
  "remove once clients migrate" comment upstream — Grouse already reads both; safe.
- `authenticate` is a no-op stub; real auth is the X-Secret-Key transport header. Correct
  to never call it.
- `elicitation.form` capability is declared and handled; non-form modes are auto-cancelled
  server-side, so Grouse's form-only handling is complete.
- goose never emits the standard ACP `plan` update — not a gap.
